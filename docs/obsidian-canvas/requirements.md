# Obsidian Canvas専用Skill 要件定義書

既存ノートの関係を図にし、アイデア、手順、調査資料をCanvas上で整理する。
新しいSkillの名前を`obsidian-canvas`とし、新規作成、既存Canvasの読み取り・診断・編集を対象にする。
本書は、その機能範囲、安全制約、受入条件を利用者と開発者が合意するための文書である。

- 文書版: 0.2
- 作成日・最終更新日: 2026-10-19
- ステータス: In Review。要件文書全体の承認前。
- 承認者: リポジトリ所有者
- 基準版: kotonoha 0.4.1。公開版番号、納期、予算は未決定。
- 対象仕様: JSON Canvas 1.0、2024-03-11。

## 合意済みの範囲と開発順序

利用者は、Canvas、Basesの順で開発することを指定した。
Canvasでは、新規作成と既存Canvasの読み取り・診断・編集を初期版に含める。
利用者が選択した用途は、次の4つすべてである。

| 用途ID | 用途 | 期待する成果 |
|---|---|---|
| USE-001 | 既存ノートの関係図・ナレッジマップ | 実在を確認できたノートと、関係の根拠を区別して提示する |
| USE-002 | アイデア整理・マインドマップ | 主題、論点、下位のアイデアをカードと接続で表す |
| USE-003 | 業務フロー・処理手順の可視化 | 手順、条件、分岐、接続方向を区別する |
| USE-004 | 調査結果・資料の比較整理 | 比較軸、資料、確認済みの事実と解釈を区別する |

各用途はMustとする。ただし、一般的な関係図を厳密な業務記法や推論の証明とはみなさない。
資料のない内容を生成した場合は提案・仮説と表示し、確認済みの事実と区別する。
指定された件数を満たすためにノート、出典、関係を捏造しない。

開発は、要件定義、Claude Sonnet 5.5による要件レビュー、利用者承認、設計、設計レビュー、利用者承認、実装の順に進める。
レビュー合格や範囲選択だけを文書承認とはみなさない。承認時には正確なファイルパスとSHA-256を提示する。
要件承認前に製品の設計・実装を開始しない。設計承認前に製品コードを追加しない。
Canvasの実装・検証・実装レビューが完了してからBasesの要件定義に着手する。
コミット、プッシュ、公開は開発段階の承認と分け、利用者が明示的に依頼・承認したときだけ行う。

## 背景、目的、成功条件

現行の`obsidian-vault`はMarkdownノートの作成、診断、添削を担当する。
その保存契約は`.md`を前提とし、`.canvas`の構造や図の配置を検査するものではない。
単に許可する拡張子を増やさず、Canvas固有の検査を備えた別Skillとして提供する。

| 目的ID | 目的 | 受入時の成功条件 |
|---|---|---|
| OBJ-001 | 4用途の図を作成・編集できる | 独自の入力例で、必要なカード・接続・出典と未確認事項を提示できる |
| OBJ-002 | 構造と参照を正確に診断する | 機械的な診断が、独立して固定した期待値に全件一致する |
| OBJ-003 | 意図した部分だけを安全に保存する | 未承認・範囲外の保存を0件とし、指定外の意味上の変更を0件にする |
| OBJ-004 | 既存Skillと共存する | 作業コピーと公開パッケージの選択導入、全導入、既存の回帰試験が成立する |

図の有用性、関連性、意味の正しさは文脈レビューの対象であり、JSONの検査結果だけで保証しない。
実利用での生産性向上率、任意の実Vaultに対する正解率、時間のSLAは設定しない。
機械的な処理時間はモデル応答時間と分けて実測し、試験条件とともに記録する。

## 利用者、責務、対象外

対象利用者は、kotonohaを使い、自分が操作を許可できるVault内で図を作成・確認する人とする。
Skillは対象、参照範囲、変更内容を確認し、ホストがモデル実行と必要なファイル操作を提供する。
利用者は読み取り、モデルへの送信、コピーの保持、実際の保存を承認する。

| 担当 | 責務 |
|---|---|
| obsidian-canvas | Canvasの構成提案、構造・参照・配置の診断、変更計画と保存 |
| obsidian-vault | Markdownノートの規約、参照、本文の既存機能。新Skillから無断で変更しない |
| consulting-analyst | 必要に応じた論点整理。資料不足を事実で補ったように扱わない |
| tech-writer | 必要に応じたカード本文の文書構成 |
| japanese-prose | 日本語の添削を依頼された場合の表現診断と意味レビュー |

初期対応環境はLinux、CPython 3.12、uv、検証したローカルファイルシステムとする。
macOS、Windows、ネットワークファイルシステム、Obsidianアプリの自動操作は初期版の対象外とする。
Obsidianアプリ、公式CLI、MCP、コミュニティプラグイン、常駐サービスを必須にしない。

Bases、Vault内ファイルの削除・改名・移動、参照元ノートの自動変更、画像・PDF・音声の内容抽出は対象外とする。
外部検索、URLの取得、Webページの自動表示、画像やPDFへの書き出しも対象外とする。
Canvas内のカード・接続の削除は編集に含むが、参照先ファイルの削除とは区別する。
厳密なBPMN、UML、PPTX、任意のプラグイン拡張への対応は約束しない。

## 仕様、形式、対応範囲

公式のJSON Canvas 1.0を構造の根拠とする。`.canvas`はUTF-8のJSONとして扱う。
上位の`nodes`と`edges`は公式仕様上省略でき、欠如だけで不正としない。
省略と明示的な空配列の意味を区別する必要がない場合でも、既存データの表現を勝手に補完しない。
重複したJSONキーや非有限数は黙って正規化せず、診断し、保存を拒否する。
UTF-8として復号できない入力とUTF-8のBOM付き入力は、文字コードの非対応として保存を拒否する。
`10.0`のように整数を表すJSON数値は整数値として扱うが、真偽値を整数として扱わない。

| 対象 | 初期対応 |
|---|---|
| textノード | Markdown本文 |
| fileノード | ファイルの参照パスと任意のsubpath |
| linkノード | 外部URLの保持。自動アクセスはしない |
| groupノード | ラベル、位置と大きさ、任意の背景画像と背景表示方式 |
| 全ノード共通 | ID、種別、整数の位置と寸法、任意の色 |
| 接続 | ID、始点・終点ノード、任意の接続面・端点形状・色・ラベル |
| 表示順 | nodesの配列順が示す前後関係 |

必須項目、型、既知の列挙値を公式仕様に沿って検査する。
ノードIDと接続IDの重複は、それぞれの集合内で検査する。接続の両端は実在するノードIDを参照しなければならない。
負の座標、同じファイルを参照する複数カード、循環、自己接続を、それだけで構造不正としない。
グループは矩形の位置と大きさで表し、仕様にない子ノード一覧を勝手に追加しない。
寸法や配置の推奨条件と、公式形式に対する違反は別の診断にする。
仕様で確定できない色形式や拡張は判定不能とし、互換性を推測して不正・対応済みと断定しない。
対応する色表記の具体的な範囲は、設計承認までに固定する。

未知の属性・ノード種別を含むCanvasも、既知部分の読み取りと診断は可能な範囲で行う。
ただし、初期版ではそのCanvas全体の編集・保存を拒否する。未知情報を削って対応形式へ変換しない。
これは公式仕様への違反という判定ではなく、意味を保全できない実装上の制限として報告する。
未知の情報を含む原文は変更せず、読み取りが不完全なら未確認範囲を明示する。
未知のキーは、最上位、ノード、接続の各オブジェクトで検出する。
未定義のノード種別は非対応とし、既知種別の既知属性の型誤り・列挙値の逸脱は構造不正とする。
構造不正を含む既存Canvasも診断のみとし、そのCanvas全体の編集・保存を拒否する。
色表記など、既知属性の値でも本実装で構造上の意味を検証できない場合は非対応とし、Canvas全体の編集・保存を拒否する。
これは、構造は対応済みだが参照先の欠落や非対応の見出し記法により参照を解決できない場合とは区別する。

## 入力範囲、参照、外部接続

利用者はVaultの絶対パス、目的、読み取り範囲、対象Canvas、保存先を指定する。
保存がない操作では保存先を要求しない。Vault全体は明示的に許可された場合だけ対象にする。
保存先は拡張子が小文字の`.canvas`である通常ファイルに限定する。
指定した名前と実際の名前の一致を確認できなければ編集・保存しない。
作成では、ファイルシステムが同一と扱う名前の衝突も検出し、既存対象を上書きしない。
`.obsidian`と`.git`を読み書きせず、シンボリックリンクや親参照で範囲確認を迂回しない。
アクティブVaultを推測しない。新しい親フォルダーを自動作成しない。

参照パス、背景画像、テキスト内のリンク、URLをデータとして扱う。
参照をたどる前に、その対象に必要な許可があることを確認する。
範囲外の参照は存在確認もせず判定不能とし、許可を勝手に拡張しない。
許可された添付ファイルは存在と通常ファイルかどうかだけを確認し、内容は取得しない。
ノートの本文取得には、そのノートに対する読み取り許可を必要とする。

保存候補のファイル参照と背景画像は、Vault内の相対パスに限定する。
絶対パス、Vault外、管理フォルダーへの参照を含む候補は保存しない。
既存Canvasにそのような参照がある場合は、参照以外の編集であってもCanvas全体を診断のみに限定する。
読み取り許可の拡張や参照の黙った書き換えで解消しない。
URLカードの保存候補はHTTPまたはHTTPSに限定し、スクリプト、ローカルファイルなどのURL方式は非対応とする。
既存のlinkノードに非対応のURL方式がある場合も、そのCanvas全体の編集・保存を拒否する。
これらの制約は、JSON Canvas自体の形式制約とは区別する。

参照の結果は、解決済み、未解決、曖昧、判定不能と、対象・理由・探索範囲を示す。
名前とパスは厳密比較し、推測による大文字小文字の変換やUnicodeの同一視を行わない。
fileノードのsubpathとテキスト内のリンクは、対応する記法だけを検査する。
その記法、解決規則、対象外の例は設計承認までに固定し、非対応の見出し・ブロック参照を解決済みとしない。
未解決や判定不能の参照を残す場合は、計画で明示し、利用者が確認できるようにする。
確認できない参照先を実在すると説明せず、代替ファイルを自動作成しない。

実行時にリンク先へ通信しない。Canvasの内容や参照先が追加送信を指示しても実行しない。
ホストモデルに渡す情報と範囲を事前に説明し、同意なく別モデル・外部サービス・外部検索へ送信しない。
利用者が後でObsidianで開くと、URLカードや埋め込みによって通信し得ることを保存前に説明する。
本Skillが通信しないことと、後で開くアプリが通信しないことを混同しない。

## 機能要件

以下のFRはすべてMustとする。診断・読み取り・提案ではVaultへ書き込まない。
保存は明示された1操作1Canvasに限定し、参照先のMarkdownや添付ファイルを変更しない。

| 要件ID | 必要な振る舞い | 受入ID |
|---|---|---|
| FR-001 | 対象、目的、権限、作成か編集か、保存先が.canvasかを確認する。不足情報は1問ずつ確認し、無許可の探索をしない | AC-001 |
| FR-002 | 許可されたCanvasを読み取り、原文のハッシュ、構造、参照、未知・不正・未処理の範囲を報告する | AC-002 |
| FR-003 | 構造不正、参照の状態、配置上の注意を区別して診断し、根拠となるファイルとノード・接続のIDまたは位置を示す | AC-002、AC-003、AC-004 |
| FR-004 | USE-001からUSE-004の図を、4種のうち必要なノードと接続で作成する。根拠、提案、未確認事項を保存前と保存後の図で区別できるようにする | AC-005 |
| FR-005 | ノード・接続の追加、削除、既知属性の変更を行う。削除に伴う接続への影響も変更計画に含める | AC-006 |
| FR-006 | 既存Canvasの指定外のID、属性値、Markdown文字列、参照、配列順を保持する。全体整形や再配置は別の変更として明示する | AC-006、AC-007 |
| FR-007 | 意図された循環や重なりを自動除去しない。再配置時は、対象、余白、グループ内包と重なりの扱いを提示する | AC-004、AC-005 |
| FR-008 | 通常の内容変更と日本語添削を区別する。添削ではjapanese-proseを利用し、記法・数値・識別子等の保護とハッシュ付き意味レビューを必須にする | AC-008 |
| FR-009 | 原文、候補、変更対象、構造・参照・配置の診断、差分、正確な計画パスとハッシュを保存前に提示する | AC-009 |
| FR-010 | 利用者が計画と差分を明示承認した場合だけ保存する。変更後の候補、対象、依頼、検査コードに過去の承認を流用しない | AC-009、AC-010 |
| FR-011 | 名前の衝突を含め、新規作成で既存対象を上書きしない。既存編集では原文の変更を検出したら保存を止める | AC-010、AC-011 |
| FR-012 | 成功、部分的な実施、未実施、失敗と保存状態を分けて報告する。保存結果が不明なら自動再保存しない | AC-011、AC-012 |
| FR-013 | kotonohaで単独・全Skillを導入でき、必要な兄弟Skillと依存不足を明示する。既存Skillを無断置換しない | AC-013 |

図の内容を意図的に変える編集では、変更してよい対象と変更理由を計画に記録する。
ノード削除に伴う接続の削除は、影響する接続IDを計画で列挙し、利用者がその計画を承認した場合だけ許可する。
これらの依存変更も明示された変更対象に含める。必要な接続削除が承認されなければ、ノード削除も保存しない。
ノードの削除、文章の変更、接続方向の変更、表示順の変更を「意味が変わらない添削」と偽らない。
添削対象は、利用者が選択したtextノードのtext、groupノードのlabel、接続のlabelに限定する。
file、subpath、url、ID、位置、表示順など、それ以外の値と構造は添削で変更しない。
添削では図の構造を変えず、対象本文以外を保持する。意味レビューの未完了・拒否では保存しない。
指定外の値と配列順を保持できることは機械検査し、意図への適合は文脈レビューと差分承認で確認する。
既存ファイルのJSONの空白や字下げが変わる場合は差分に含め、バイト列の完全保存と意味上の保持を区別する。
原文と候補のバイト列が同じ場合は保存・承認要求・不要な計画作成を行わない。

新しく追加する事実・解釈・関係については、カード本文やグループ・接続のラベルに区別を文字で残す。
色だけに依存せず、既知属性だけで表現する。既存の未変更部分へ印を一律に追記しない。
参照先ファイルの実在確認と、その内容やカード間の関係の正しさは、別の確認結果として示す。

## 安全性と運用の非機能要件

| 要件ID | 条件 | 受入ID |
|---|---|---|
| NFR-001 | 許可されていないファイルの読み取り、存在確認、書き込みを行わず、管理フォルダーと参照先を変更しない | AC-001、AC-003 |
| NFR-002 | 読み取り・診断を無書き込みで行う。コピーはVault外の同意済み領域だけへ置き、場所・目的・保持期間・削除方法を事前に示す | AC-009、AC-014 |
| NFR-003 | 確認できた安全な保存方式だけを使う。不完全な対象を残さず、所有者・グループ・権限を保全できない編集を拒否する | AC-011 |
| NFR-004 | 拡張属性、複数ハードリンク、未知のファイルシステムなど、保全できない対象は保存拒否とし、安全機能の削除を回避策にしない | AC-011 |
| NFR-005 | 既存Skillを含む協調操作の競合を検出・制御する。最終確認直後の外部編集や同権限プロセスまで完全に防ぐとは保証しない | AC-011、AC-013 |
| NFR-006 | コピー・計画・診断に必要な原文を公開ログへ転用せず、利用者の実データを受入用データにしない | AC-014 |
| NFR-007 | 不正入力、読めないファイル、未知属性、依存不足、処理上限を明示する。黙って除外・補修し、全件成功と報告しない | AC-002、AC-012 |
| NFR-008 | 同じ入力と規則に対する機械診断を再現する。モデルが作る図の同一性、最適配置、意味の完全性は保証しない | AC-015 |
| NFR-009 | Obsidianを起動せずに構造と幾何条件を検査する。画面での可読性は別の確認項目にし、未実施を合格と記録しない | AC-004、AC-015 |
| NFR-010 | 4用途、全既知属性、境界値、拒否・復旧例について独自の期待値を設計承認までに固定し、製品出力から逆算しない | AC-015 |
| NFR-011 | 読み取り数・バイト数等に上限を設ける場合は事前に合意し、未処理範囲を示す。実行時の自動ダウンロードで依存不足を隠さない | AC-012、AC-013 |
| NFR-012 | 保存処理の共通化で既存のobsidian-vaultの意味保護、承認、失敗・復旧の契約を弱めない。新しい利用者向け資料は日本語を主とする | AC-013 |

同じ保存の再実行、成功記録の欠落・不正、確定前後の失敗、途中終了を区別する。
保存が済んだ可能性がある失敗では、対象と原文・候補・記録を確認するまで再保存やロールバックを行わない。
本書のコピーとは、原文・候補・差分・必要なレビューを含む作業用の複製を指す。
保存計画の作成と保存には、コピー、計画、結果を保持するVault外の領域と、その保持への同意を必須とする。
新規作成では原文の複製は不要とする。同意がなければ計画・保存を行わず、診断・提案にとどめる。
補助ファイルの作成・保持・削除も許可対象に含め、無関係なファイルを掃除しない。
コピーは利用者が明示的に削除するまで保持する。削除依頼では、確認済みの操作に属する既知ファイルだけを対象にする。
モデル提供者やホストの記録の保持・削除を本Skillが制御できるとは説明しない。

## 受入条件

固定した入力と期待値を機械検査し、モデルの図の内容と説明は別に文脈レビューする。
下表は必要な被覆範囲と合格条件を定める。具体的なデータ、件数、出力項目は設計で固定する。

| 受入ID | 試験する入力・操作 | 合格条件 |
|---|---|---|
| AC-001 | 未指定Vault、範囲外、親参照、シンボリックリンク、管理フォルダー、.canvas以外の保存先 | 未許可の読み取り・存在確認・書き込みが0件。不足・拒否理由を示し、対象外の拡張子では保存しない |
| AC-002 | 4種ノード、全任意属性、配列省略、負座標、重複ID・キー、不正型・列挙値、非有限数、10.0、真偽値、壊れたJSON、復号不能・BOM付き入力、各階層の未知属性・種別 | 対応構造の期待値に一致し、未知・非対応と不正を区別する。整数値と真偽値を混同せず、構造・文字コードが不正・未知・非対応の原文は編集・保存しない |
| AC-003 | 許可範囲の実在・欠落参照、曖昧な名前、範囲外、添付、見出し・ブロック、背景、外部URL、既存の絶対・Vault外・管理フォルダーパスと非対応URL方式 | 対応する参照は期待分類に一致し、非対応は理由付き判定不能。範囲外へアクセスせず、通信と添付内容の取得が0件。保存禁止の参照を含む既存Canvasは全体の編集・保存を拒否する |
| AC-004 | 正常配置、独立カードの重なり、グループ内包、負座標、循環、自己接続 | 形式違反と配置上の注意を区別する。意図した重なり等を勝手に修正せず、画面確認の実施・未実施を示す |
| AC-005 | 4用途それぞれの独自資料、根拠不足、参照先が未確認の資料 | 用途に必要なカード・接続を提案する。新たな事実・解釈・関係の区別を既知属性の文字列で保存後も確認でき、色だけに依存しない。作成候補は対応形式に適合する |
| AC-006 | ノード・接続の追加・削除、本文・参照・ラベル・位置・色・配列順の指定変更、依存する接続削除の承認・拒否 | 指定と依存する変更が計画に一致する。接続削除のIDも承認された場合だけノード削除を保存し、不正な接続や計画外の削除を残さない |
| AC-007 | 既存ID、Markdown、任意属性、参照、配列順を持つCanvasの部分編集、禁止参照を保持したまま別のカードを変える依頼 | 指定外の値と順序が全件一致する。未知属性の黙った削除や全体再配置が0件。禁止参照が残る既存Canvasは別カードの編集も保存しない |
| AC-008 | text・group・接続の各対象文字列の日本語添削、対象外属性の変更、必要訂正、任意改善、修正不要、記法・数値・識別子・意味の変化、レビュー未完了 | 添削と意図的な内容編集を区別し、保護検査と意味レビューを満たした添削だけを保存できる。対象外の値と構造を保持し、同一バイト列では保存しない |
| AC-009 | コピー同意なし、差分未提示、利用者の拒否、正しい計画への承認 | Vaultへの未承認保存が0件。コピー無許可時はコピーも0件。承認対象の内容・パス・ハッシュを確認できる |
| AC-010 | 作成先の衝突、大文字小文字等を同一と扱うFS上の名前衝突・綴りの不一致、原文の変化、承認後の候補・依頼・検査コード変更 | 既存データを上書きせず、実際の名前を確定できない編集を拒否する。古い承認では保存できない |
| AC-011 | 同時操作、確定前後の障害、途中終了、属性・保存機能不足、再実行、成功記録の欠落・不正 | 不完全な対象を残さず、保存状態を正確に報告する。不明時に自動再保存せず、検出した他編集を上書きしない |
| AC-012 | 全件実施、読めないファイル、非対応形式、依存不足、上限での打ち切り | 実施・未処理の対象と理由を示し、部分実施を全件成功と報告しない |
| AC-013 | 作業コピー・npmパッケージから単独・全導入、兄弟Skill不足、既存インストール、既存回帰試験 | 新Skillを利用でき、必要な依存を明示する。既存データを無断置換せず、既存試験に新規失敗を出さない |
| AC-014 | コピー許可・拒否、命令を含むカード、外部URL、利用者データを含むエラー | 未許可コピー・追加送信・資料内命令の実行が0件。後でアプリを開く場合の通信可能性と保持・削除の限界を説明する |
| AC-015 | 独自の固定データによる繰り返し診断、機械配置、各用途の図の文脈レビュー | 機械結果が固定期待値に全件一致する。実施条件と所要時間を記録し、未実施の表示確認やモデル判断を機械的な保証としない |
