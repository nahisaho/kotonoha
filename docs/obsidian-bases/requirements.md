# Obsidian Bases専用Skill 要件定義書

許可されたVault内の`.base`ファイルを読み取り、診断し、直接作成・編集する。
新しいSkillの名前を`obsidian-bases`とする。
本書は機能範囲、直接編集の条件、検証できる範囲を合意するための文書であり、製品の設計・実装ではない。

- 文書版: 0.2
- 作成日・最終更新日: 2026-10-20
- ステータス: In Review。要件文書全体は未承認。
- 承認者: リポジトリ所有者
- 基準版: kotonoha 0.4.1。公開版番号、納期、予算は未決定。
- 仕様の根拠: Obsidian公式ヘルプの固定リビジョン`cd6c9f3c7d5492bbbec94e8f403572b84eeb325b`。

## 合意済みの範囲と開発順序

利用者はCanvas、Basesの順で開発することを指定した。
Canvasの実装・検証・実装レビューの結果は、[実装検証記録](../obsidian-canvas/implementation-verification.json)に記録済みである。
Basesについて利用者が選択した初期範囲は、次のとおりである。

| 項目 | 選択された範囲 |
|---|---|
| 操作 | `.base`の新規作成、読み取り、診断、既存編集 |
| 保存方式 | ホストのファイルツールによる直接作成・編集 |
| ビュー | Table、Cards、List、Kanban |
| バージョン条件 | KanbanはObsidian 1.14以降。Table・Cardsは1.9以降、Listは1.10以降という公式資料の条件を区別する |
| ノートの変更 | 本文とプロパティ自体の変更は本Skillの対象外。必要ならobsidian-vaultで別の許可を得る |

対象、変更内容、保存までを利用者が明示していれば、その範囲で直接保存できる。
専用の保存CLI、外部の計画ファイル、計画ハッシュへの毎回の承認を必須にしない。
ただし、提案だけの依頼は書き込み許可ではない。保存前の差分確認を求められた場合は、承認まで保存しない。

開発は要件定義、Claude Sonnet 5.5によるレビュー、利用者承認、設計、設計レビュー、利用者承認、実装の順に進める。
機能範囲の選択やAIのレビューを、要件文書全体への承認とみなさない。
各段階の承認時には、正確な全対象パス、SHA-256、残る制約を提示する。
要件承認前に製品設計を始めず、設計承認前に製品コードや配布Skillを追加しない。
コミット、プッシュ、公開は別の明示的な依頼・承認がある場合だけ行う。

## 背景、目的、成功条件

Basesはノートやファイルをプロパティで表示・絞り込みする機能であり、別のデータベースへ情報を複製する仕組みではない。
`.base`はビュー、フィルター、数式などを記述するYAMLファイルである。
obsidian-vaultはMarkdown、obsidian-canvasはJSON Canvasを扱うため、Bases固有の構造と式の扱いを別Skillに分離する。

| 目的ID | 目的 | 成功条件 |
|---|---|---|
| OBJ-001 | 必要な一覧と可視化を作る | 4種類のビューについて、独自の資料と期待値を使って候補を作成・編集できる |
| OBJ-002 | 形式と未確認事項を区別する | YAML・対応構造の機械検査と、式の実行結果・画面表示の未確認を混同しない |
| OBJ-003 | 許可された変更だけを保存する | 範囲外・未許可の書き込みを0件とし、変更対象以外の値・順序・コメントを保持する |
| OBJ-004 | 直接編集の限界を明示する | 保存後に読み戻し、競合・途中失敗を成功と報告せず、専用CLIと同じ保証を主張しない |
| OBJ-005 | 既存Skillと共存する | 選択導入と全導入が成立し、既存Skillを無断置換せず、既存の回帰試験に新規失敗を出さない |

Skill指示への適合と、ホストが強制するアクセス制御は別である。本Skillをホスト全体のサンドボックスとは説明しない。
任意のVaultに対する正解率、結果集合の完全再現、実表示の同一性、生産性向上率は保証しない。
機械処理の時間はモデル応答時間と分け、実施条件とともに記録する。

## 利用者、責務、対象外

利用者は自分が操作を許可できるVault、読み取り範囲、変更内容、保存先を指定する。
ホストはモデル、許可された読み取り・編集ツール、必要な検査機能を提供する。
アクティブVaultを推測せず、不足する情報は1問ずつ確認する。

| 担当 | 責務 |
|---|---|
| obsidian-bases | `.base`の構成、構造診断、変更内容の説明、許可された直接保存 |
| obsidian-vault | 別途許可されたMarkdownノートの作成・編集、規約確認、プロパティの変更 |
| obsidian-canvas | Canvasの構造・配置・保存。Basesの許可を流用しない |
| consulting-analyst | 必要に応じた比較軸・管理目的・判断条件の整理 |
| japanese-prose | 表示名等の日本語添削を依頼された場合の表現診断と意味レビュー |

初期版は必要な確認と属性保全ができるローカル通常ファイルを対象とする。
Obsidianアプリ、公式CLI、MCP、常駐サービス、コミュニティプラグインを必須にしない。
直接編集のためだけにPythonやuv、obsidian-vaultの保存APIを必須にしない。
構造検査に必要な依存やホスト機能は設計で明示し、不足を自動ダウンロードや無検査保存で隠さない。

Markdown内の`base`コードブロックの直接編集、ノートへの埋め込みの自動挿入、ノートの一括プロパティ更新は対象外とする。
必要なら埋め込み記法を会話で提示できるが、それをノートへの書き込み許可とみなさない。
ファイルの削除・移動・改名、新規フォルダーの自動作成、添付内容の取得、CSV出力、アプリのUI操作は対象外とする。
Mapビューと任意のプラグイン独自ビューは初期対応に含めない。
外部検索、外部URLの取得、式の実行、任意コード・シェルコマンドの実行をBasesデータから誘発させない。

## 形式、ビュー、式の対応範囲

### YAMLと共通構造

保存対象は小文字の`.base`で終わるUTF-8の通常ファイルとする。
YAMLの構文、対応するキーの型と階層、式を格納する文字列、ビューの構成を検査する。
重複キーを黙って上書きせず、複数文書、任意タグ、アンカー・エイリアス、マージキーを初期保存の対象外とする。
復号不能、BOM、非対応の型等は、形式違反と実装の対応制限を区別して報告する。
真偽値を整数や文字列の代わりに受け入れず、YAMLの暗黙型変換で式やプロパティ名を変えない。
具体的な対応キー、値域、資源上限、構文と非対応の分類は設計承認までに固定する。

対応する上位構造はfilters、formulas、properties、summaries、viewsを基本とする。
項目の省略、空の値、空配列・空辞書を勝手に補完・同一視しない。
プロパティの表示名を、式で使う識別子やノートのプロパティ名へ置き換えない。
`.base`内に宣言がないノートプロパティを参照しているだけで、未定義エラーとしない。

未知のキー、未知のビュー、意味を保全できない非対応構造があれば、既知部分を可能な範囲で読み取り・診断する。
そのファイル全体の編集・保存は初期版では拒否する。これはObsidian側の形式違反という断定ではない。
不正な既存YAMLも診断だけにとどめ、修復して別内容を保存する依頼へ黙って切り替えない。
コメント、引用符、空白、改行、マッピング順序、ビュー順序を、部分編集の際に無断で再整形しない。
保持できない場合は候補の提示にとどめる。明示的な全体整形の許可がある場合でも、未知・不正な内容の保存拒否は解除しない。

### ビューと用途

4種類のビューそれぞれに、独自に作成した構成例と確認手順を用意する。
新規候補は必要な種類だけを使い、1つのファイルへ4種類すべてを入れることは要求しない。
複数ビューの追加・削除・並べ替え、名前、表示プロパティ、フィルター、対応する並び順・グループ設定を扱う。
同名ビューが存在した場合は編集対象の曖昧さを報告し、先頭を推測して変更しない。
同名であること自体を、公式仕様で確認していない形式違反とは断定しない。

| 用途ID | ビュー | 独自の受入用例 | 確認する内容 |
|---|---|---|---|
| USE-001 | Table | 状態・期限・担当を確認する案件一覧 | 表示列、条件、並び順、集計設定の意図 |
| USE-002 | Cards | 資料・読書候補のカード一覧 | 表示項目、画像設定の対応範囲、外部画像を取得していないこと |
| USE-003 | List | 選択したノートの索引 | 主項目、追加項目の順序、マーカー等の対応範囲 |
| USE-004 | Kanban | 状態ごとにまとめる作業一覧 | グループとなるプロパティ、グループ順・非表示条件、必要なアプリ版 |

これらは受入のための提案例であり、利用者の実データや規約を確認した事実とは扱わない。
公式資料がYAMLのキーと値を明示していないUI設定は、対応済みと推測しない。
各ビューで直接編集できる具体的な設定範囲は、公式根拠と独立した入力例を添えて設計承認までに固定する。
最低対応範囲には、公式資料がキーを明示しているfilters、formulas、properties、summaries、viewsと、ビュー共通のtype、name、filters、order、limit、groupBy、groupOrder、summariesを含める。
各キーは公式に示された適用箇所で扱い、ビューが利用しない設定を一律に追加しない。
4ビューのそれぞれで、少なくとも新規作成、名前・表示項目・フィルターの既存編集ができることを要求する。
Kanbanでは必須のグループ設定も作成・編集できなければならない。
根拠不足等でこの最低範囲を満たせない場合は、非対応の具体例と削減内容を提示して要件を再承認する。
要件を再承認せずに、作成のみ・診断のみのビューを「作成・編集対応」として設計承認へ進めない。
Kanbanのグループ設定と、アプリ上のカード移動によるノート・ファイル変更は別である。
本Skillはカードを移動せず、ノートのプロパティやファイルの場所も変更しない。

### フィルター、数式、集計

全体フィルターとビュー単位のフィルターを区別する。両方がある場合はANDで適用されるという公式の意味を保つ。
and、or、notの入れ子、式の文字列、式・集計の定義と参照を対象とする。
並び順、括弧、演算子、文字列リテラル、識別子を、見た目を整える目的で変更しない。
組み込み集計の選択と独自集計の定義を区別し、ビューへの割り当てを別に確認する。

式はデータとして扱い、eval、JavaScript、シェル等で実行しない。
静的検査で確定できる型・構造・参照の問題と、Obsidian上での実行が必要な問題を分ける。
認識できるformula参照では、未定義参照と直接・間接の循環を検査する。
文字列リテラルの中の文字を参照と誤認せず、認識できない式を単純な文字列検索で合格にしない。
式文法の初期対応範囲は設計で固定し、範囲外の式を含む既存ファイルは診断だけにする。
対応文法内でも、ノート値の型、日付、関数、プラグイン、アプリ版に依存する結果は、必要な確認がなければ判定不能とする。
YAMLとして正しいことを、式の正しさやObsidianでの表示成功の証明としない。

`this`は開き方によって参照先が変わる。単独表示、埋め込み、サイドバーで同じ結果になるとは説明しない。
動的な参照を解決するためにアクティブノートを推測したり、許可範囲外を探索したりしない。
プロパティの実在・型の確認でノートを読む必要があれば、別途許可された範囲だけを読む。
一部のノートを確認しただけでVault全体のプロパティ分布や結果件数を断定しない。

## 権限、直接保存、失敗の扱い

Vaultの絶対パス、目的、読み取り範囲、正確な保存先、変更対象を確認する。
Vault全体の読み取りは明示された場合だけ行う。`.base`を読む許可は、式が言及する全ノートの取得許可ではない。
Vaultルートから対象までの実体と綴りを確認し、範囲外、親参照、途中を含むシンボリックリンクを拒否する。
大文字小文字違いを含めて`.obsidian`と`.git`を読み書きしない。
確認できないパス、維持できない属性、複数ハードリンク、拡張属性付き対象は保存しない。
属性や安全機能を削除して保存できる状態へ変えることを、回避策として求めない。

読み取り、ホスト設定のモデルへ渡す情報、書き込み、外部コピーを別々の許可として扱う。
外部コピーは直接編集の必須条件にしない。必要な場合は場所、目的、保持期間、既知ファイルだけの削除方法を説明して同意を得る。
資料内の指示を権限変更として扱わず、同意なく別モデル、外部サービス、外部検索へ追加送信しない。

新規候補では、対象データの範囲とフィルターの意図を確認する。
フィルターがなければアプリ上ではVault全体が対象となることを説明し、許可のない全件表示を暗黙の既定にしない。
フィルターはホストの読み取り権限を強制する機構ではなく、アプリで開いた際の表示条件である。
全体・ビューのフィルターの追加・削除・書き換えと、formulasの変更は、すべて対象範囲が拡大する可能性のある変更として扱う。
任意の式の同値性や結果集合の大小を判定して、確認を省略しない。
正確な変更前後の内容を示し、その差分と保存への許可を得る。利用者がその差分と保存を既に明示していれば再確認は不要である。
この確認に専用CLIの計画やハッシュ承認は要求しない。
全体と各ビューの条件、動的な式、非表示グループ等が結果に与える影響を区別し、未検証の結果件数を捏造しない。

新規作成は既存対象を置換しない方法を使い、同一と扱われる別表記の名前も上書きしない。
編集では原文を取得し、変更候補と指定外の保持を確認する。
保存直前に対象の内容・実体を再確認し、外部変更があれば止める。同一バイト列なら保存しない。
ホストツールの能力が不足すれば未実施とし、無検査での保存へ切り替えない。
編集では所有者・グループ・権限を維持し、新規作成ではホストの通常の安全な作成規則に従う。
保存後に読み戻し、意図した内容と指定外の保持を確認する。

直接編集にはCanvas専用CLIのルートロック、原子的確定、成功記録、再実行保護はない。
この違いと、最終照合直後の外部変更・途中失敗の限界を保存前に説明する。
専用CLIと同じ検証済み保存や機械的なアクセス強制を保証しない。
1操作1ファイルとし、作成・編集に必要な許可を他のファイルへ流用しない。

結果は提案、変更なし、未実施、部分的な診断、確認済みの保存、失敗・保存結果不明を区別する。
編集ツールのエラーや読み戻し不一致があれば、保存結果を確認できないと明示する。
同じ操作を自動再保存せず、原文へのロールバックも行わない。対象の確認後、必要な対応への新しい許可を得る。
実行していないCLIの結果JSON、成功記録、人間の承認を捏造しない。

Cards等の画像やリンクによって、利用者が後でアプリを開く際に通信する可能性を説明する。
本Skillで通信しないことと、アプリで開いても通信しないことを混同しない。
実際に画面確認を行っていなければ、表示確認は未実施とする。

## 受入条件

独自の固定入力と期待値を使い、機械検査、ホスト操作、文脈レビュー、アプリの表示確認を分ける。
直接編集の指示は実行時にモデルが従う規則であり、試験に成功しても任意のホストを強制隔離できるとは主張しない。

| 受入ID | 入力・操作 | 合格条件 |
|---|---|---|
| AC-001 | 未指定Vault、範囲外、管理パス、親参照、ルート・途中・対象のシンボリックリンク、非`.base` | 未許可の取得・存在確認・書き込みが0件。確認できない場合も保存しない |
| AC-002 | 対応YAML、型誤り、重複キー、壊れたYAML、複数文書、タグ・エイリアス、復号不能、BOM、未知キー・ビュー | 固定した分類・位置・理由に一致し、不正・非対応の既存対象へ書かない。黙った補修・正規化が0件 |
| AC-003 | 入れ子のand/or/not、全体とビューの条件、数式・集計の参照、循環、リテラル中の識別子風文字列、非対応関数や文法、命令風文字列 | 構造と式の診断が期待値に一致し、式や命令の実行が0件。静的合格を実行成功としない |
| AC-004 | 4ビューの独自用途、対象版が不明・不足、Kanbanのグループ不足、編集非対応の独自例 | 4ビューすべてで新規作成と最低対応範囲の既存編集を実証する。非対応例は理由付き拒否とし、対応済みと報告しない。版条件を説明し、捏造したプロパティや確認済み表示を示さない |
| AC-005 | ビュー追加・削除・並べ替え、名前・表示列・条件・集計の部分編集、同名ビュー、公式に明示された最低対応キー | 変更が許可された対象に一致し、最低対応キーの作成・編集を独立例で確認する。指定外の値・順序・コメントを全件保持し、曖昧な対象を推測しない |
| AC-006 | 作成・編集・保存を明示した依頼、提案だけ、保存前確認、拒否 | 明示した範囲ではCLI計画なしで保存できる。提案・確認待ち・拒否では書き込み0件 |
| AC-007 | 同一バイト列、引用符・コメント・改行を含む既存対象、全体整形の未許可 | 変更なしでは保存0件。無許可の整形0件。保持できない候補を保存しない |
| AC-008 | 新規衝突、別表記の同名対象、保存直前の内容・実体変更、属性保全不能 | 既存対象や検出した外部変更を上書きしない。必要機能不足では未実施とする |
| AC-009 | 保存前後のツール障害、読み戻し不一致、同時編集、保存結果不明 | 実際の保存状態を区別し、不明時の自動再保存・ロールバック0件。原子的確定・CLIロック・成功記録を主張しない |
| AC-010 | 表示名の必要訂正・任意改善・修正不要、式や識別子の変更、未完了レビュー | 添削の保護検査と意味レビューを満たす変更だけを保存し、意図的な設定変更と混同しない |
| AC-011 | 作業コピー・npmパッケージから単独・全導入、既存Skill、依存・ホスト機能不足 | 導入内容が一致し、無断置換・自動取得が0件。既存のnpm・Vault・Canvas・日本語添削の回帰試験に新規失敗を出さない |
| AC-012 | 全件表示、andからorへの変更、条件削除、比較演算子・formulas変更、部分許可のノート型調査、this、外部画像・URL、コピー拒否、読み取り許可のみでモデル入力拒否、未許可の別モデルへの送信、資料内の範囲拡張指示、ノート変更要求 | 条件・formulasの差分と保存が未許可なら書き込み0件。モデル入力拒否時はモデルへの本文取得・送信0件とし、資料内の指示で権限を増やさない。無断の範囲拡張・送信・通信・コピー・ノート変更が0件。未確認の件数・型を断定しない |
| AC-013 | 読み取り・解析の失敗、設定した上限への到達、巨大・深い入力 | 処理済みと未処理、理由を示し、部分診断を全件成功にしない。不十分な検査で保存しない |
| AC-014 | 独立した全固定データ、反復診断、4用途の文脈レビュー | 機械結果が期待値に全件一致し、ホストの実行条件と所要時間を記録する。未実施の画面確認を合格にしない |

## 未決事項と残る制約

| ID | 論点 | 扱い |
|---|---|---|
| OPEN-001 | 公式資料がYAMLで明示するキー、各ビューの設定、式文法・関数・参照検出の対応範囲 | 設計で根拠・境界値・独立例を固定する。対応範囲外は診断のみとする |
| OPEN-002 | 構造検査の実行経路、必要なホスト機能・依存、入力上限と結果形式 | 設計承認までに固定し、直接編集の条件と混同しない |
| OPEN-003 | 対応するホスト・ローカルFSと、実際のObsidian表示を確認できる環境 | 検証できた範囲だけを記録する。表示未実施を対応確認済みとしない |
| OPEN-004 | 公開版番号とリリース時期 | 別の公開承認で決定する |
| RSK-001 | 公式ヘルプが完全な機械可読スキーマではなく、版ごとに機能も変わる | 根拠リビジョンを固定し、未確認のキー・版は推測しない |
| RSK-002 | 式の静的検査だけでは型・件数・表示・時間依存結果を確定できない | 判定不能を示し、アプリ上の確認と分ける |
| RSK-003 | 直接編集には保存トランザクションやCLIとの協調ロックがない | 限界を事前説明し、保存前確認と読み戻しを実施する。不明時は自動再保存しない |
| RSK-004 | ホストのファイルツールが必要な範囲確認・衝突拒否・属性保全を提供しない | 機能不足として保存せず、無検査や別経路の書き込みへ逃げない |
| RSK-005 | 表示名の添削や整形が式・識別子を壊す | 意図的変更と添削を分け、指定外の保持と意味レビューを行う |

要件承認後の設計では、隔離した使い捨ての実現可能性検証を行う。
構造検査、直接編集で利用できるホスト機能、全入力形、拒否・競合・結果不明の扱いを先に確かめる。
検証コードを製品コードへ流用せず、実装後の受入試験の代わりにしない。
実行契約の正本、固定manifest、機械検証を先行したリスク別レビューを使い、設計承認までに独立した期待値を用意する。
