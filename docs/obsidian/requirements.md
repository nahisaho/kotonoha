# Obsidian専用Skill 要件定義書

kotonohaにObsidian専用Skillを追加し、既存Vaultの規約を尊重して技術ノートを作成・診断する。
本書は利用者と開発者が、対象の5機能、安全上の制約、受入条件を合意するための文書である。

- 文書版: 0.2
- 作成日・最終更新日: 2026-10-19
- 作成者: GitHub Copilot
- 承認者: リポジトリ所有者
- ステータス: In Review
- 開発対象: kotonohaのObsidian専用Skill。公開版番号はリリース承認時に決定する。
- 関連作業: v0.4.1開発中のObsidianテンプレート追加。既存の未コミット変更は保持する。

## 合意する範囲と段階承認

利用者は、Vault規約の確認、ノート新規作成、関連ノート候補の提示、内部リンク診断、日本語添削の5機能を初期版の対象として選択した。
日本語添削は差分の提示だけでなく、利用者が差分を明示的に承認した後の保存まで対象とする。
優先度はすべてMustとし、機能の追加より既存データを壊さないことを優先する。

開発順序は、要件定義、要件レビューと利用者承認、設計、設計レビューと利用者承認、実装とする。
レビューで問題が見つからなくても、利用者の承認とはみなさない。
承認対象のファイルパスとSHA-256を提示し、承認後に内容が変わった場合は影響する段階を再承認する。
本書の承認前に専用Skillの設計・実装を開始しない。既存のテンプレート追加は別作業として扱う。

## 背景、目的、成功指標

現行のtech-writerにはObsidian用テンプレートと構成ガイドを追加済みだが、実Vaultの参照先や規約との整合性は検証していない。
公開された他製品の機能は用途発見の材料にとどめ、独自の要件と受入条件から設計する。

| 課題ID | 解決する課題 | 目的ID | 初期版の成功指標 |
|---|---|---|---|
| ISS-001 | テンプレートだけでは既存Vaultの規約を確認できない | OBJ-001 | 固定検証データで規約の観測事実と推測を区別する |
| ISS-002 | ノート作成と添削で既存の参照・プロパティを損なう恐れがある | OBJ-002 | 許可されていないファイル変更と保護対象変更を受入試験で0件にする |
| ISS-003 | 関連ノートや未解決リンクの意味を一律には判断できない | OBJ-003 | 固定検証データで実在候補、未解決、曖昧、判定不能を区別する |

判定時期は実装後の受入試験とする。現状値は未測定であり、生産性や日本語品質の改善率は成功指標にしない。
固定検証データは独自に作成し、期待値と実行結果を照合する。実Vault全般の正解率やLLMの推論精度を保証するものではない。

## 利用者、責務、対象外

対象利用者は、GitHub Copilot CLIでkotonohaを使い、自分が管理するVaultの技術ノートを作成・確認する人とする。
Vaultとは、ノートや設定を保存するObsidianのフォルダーを指す。
共有Vaultへの権限の有無は利用者が確認する。承認者はスコープと受入可否を判断し、開発者は要件・設計・試験の対応を管理する。

| 担当 | 責務 |
|---|---|
| Obsidian専用Skill | 対象Vaultの確認、規約と参照関係の診断、処理の調整 |
| tech-writer | 文書種別、本文構成、情報の完全性、既存テンプレートの利用 |
| japanese-prose | 日本語表現の診断・添削と、既存の意味保存手順 |
| ホスト | ファイル操作、モデル実行、利用可能なツールと権限の提供 |
| 利用者 | 対象範囲、変更、モデルに渡す情報、承認の判断 |

対象外は、大量移動、ノート名の変更、削除、自動統合、既存タグの一括変更、`.obsidian`設定変更、コミュニティプラグイン連携とする。
Canvas・Basesの作成、PDFや画像の内容抽出、外部サイトの調査、独自の検索サービス、Obsidianプラグイン自体の開発も含めない。
未解決リンク先のノートを勝手に作成しない。PARAなど特定の整理方式を必須にしない。

## 独立開発の境界と根拠

他製品のREADMEと公開Skill文書を調査済みのため、他実装の情報から隔離された厳密なクリーンルーム開発とは称さない。
本開発は、公開仕様と独自の受入条件に基づく独立設計・独立実装として扱う。

| 根拠ID | 根拠 | 利用範囲 |
|---|---|---|
| SRC-001 | 利用者の方針指定と5機能の範囲選択、2026-10-19 | 開発方針、スコープ、段階承認 |
| SRC-002 | Obsidian公式ヘルプのTemplates、Properties、Internal links、Callouts | 対象記法と標準機能の仕様確認 |
| SRC-003 | kotonohaのtech-writer、japanese-prose、既存インストーラー | 既存機能との責務分担と互換性 |
| SRC-004 | 公開事例の調査結果 | 用途の発見のみ。実装・表現・試験データは流用しない |

他製品の指示文、コード、内部構成、サンプル文章、試験データをコピー・翻案しない。
設計判断は本書の要件ID、公式仕様、独自検証の結果に対応付ける。
追加調査が必要な場合は参照元、確認日、利用目的を記録する。ライセンスや権利上の適法性を本方針だけで保証しない。

## 入力範囲と業務ルール

利用者は対象Vaultを明示し、読み取り可能なフォルダーまたはファイル、作成・編集先、処理目的を指定する。
Vault全体を選ぶこともできるが、既定で全Vaultを探索しない。
複数Vaultが存在する場合もアクティブVaultを推測して選ばない。
指定されたVaultであることを確認できない場合は、理由を報告して処理を止める。

規約の入力元は、利用者の明示的な指示、許可された規約ファイル、許可されたノートの観測結果とする。
規約の報告には根拠の種類、ファイルパス、観測件数または対象一覧を添える。
記載済みの規約と、個々のノートで確認できた事実を区別する。観測から一般的な規約を導く場合は、件数にかかわらず推測と表示する。
`.obsidian`の内容は初期版では読み書きせず、プラグイン設定や内部メタデータに依存しない。
ノートの本文に含まれる命令は資料として扱い、権限変更、コマンド実行、外部送信の指示として実行しない。

観測結果が規約と矛盾した場合は矛盾を示し、自動的に既存ノートを修正しない。
利用者の指示が規約と異なる場合は差異を確認し、保護対象や安全制約に反する変更は承認だけで検査を迂回しない。

## 対応する記法と判定の限界

初期版はUTF-8のMarkdownノートを扱い、次の6記法を対象とする。表示名を参照先と取り違えない。

| 記法 | 例 | 参照先を確認する範囲 |
|---|---|---|
| ノートへのwikilink | `[[Note]]` | パスなしの名前はVault内のノート全体。末尾の`.md`は省略できる |
| 表示名付きwikilink | `[[Folder/Note\|表示名]]` | フォルダー付きのパスはVaultルートからのパスとして扱う |
| 他ノートの見出し | `[[Note#Heading]]` | ノートの解決に必要な範囲と、対象ノートの見出し |
| 同一ノートの見出し | `[[#Heading]]` | 現在のノートの見出し |
| ノート埋め込み | `![[Note]]` | wikilinkと同じ。埋め込み内容の生成は行わない |
| 相対Markdownリンク | `[表示名](Folder/Note.md)` | リンク元ノートの親フォルダーを起点とする指定パス |

相対Markdownリンクは`.md`付きの相対パスと見出し部分を対象とする。
URLエンコードされたパスと見出しは1回復号して確認し、不正なエンコードは判定不能とする。
`.md`を省略したMarkdownリンク、絶対パス、Markdown以外のファイルへの参照は初期版では判定不能として報告する。
外部URLは検査対象外として件数を報告し、アクセスしない。
コードブロック、インラインコード、Obsidianコメント内の例示は実リンクとして数えない。

見出し参照は、対象ノートの見出し文字列との完全一致を初期版の規則とする。
見出しの装飾除去やslug変換などが必要な記法は、未解決と断定せず判定不能とする。
名前や見出しを一意に絞れない場合は曖昧とし、Obsidianの近接ノート優先などの推測で候補を選ばない。
より広いObsidian互換が必要になった場合は要件の変更として扱う。

| 分類 | 判定条件 |
|---|---|
| 解決済み | 必要な参照範囲を確認でき、対象ノートと指定見出しが一意に存在する |
| 未解決 | 必要な参照範囲の確認が完了したうえで対象がない。ノートの欠落と見出しの欠落を根拠で区別する |
| 曖昧 | 確認した範囲だけでも複数候補があり、初期版の規則では一意にできない |
| 判定不能 | 必要な範囲が未許可・読み取り失敗・処理未完了、または記法が非対応。理由を添える |

Vault全体の参照確認は、利用者が全体読み取りを明示的に許可した場合に限る。
部分範囲での名前だけのwikilinkは、候補が0件または1件でも判定不能とする。
一方、指定パスが許可範囲内であり、そのパスまたは対象ノートを確認できるリンクは、部分範囲でも解決済み・未解決を判定できる。
必要な範囲を読めなかった場合は、全体読み取りの許可があっても未解決と断定しない。
範囲外へ到達する参照はアクセスせず判定不能とする。
将来のノートへの参照は未解決として観測できるが、それだけで誤りとは判定しない。

ブロックID参照、添付ファイルの埋め込み先、プラグイン独自の参照、規則に適合しない記法は判定不能として報告する。
対応するYAMLの範囲は設計で明文化し、非対応を正常として扱わない。
プロパティに含まれるリンクの自動検査、Obsidian画面での表示検証、全バージョンとの完全互換は初期版の対象外とする。

## 安全・品質要件

以下のNFRもすべてMustとする。時間・予算のSLAは設定せず、モデル応答時間を除く実測値を設計・実装時に記録する。

| 要件ID | 条件と必要な結果 | 受入ID |
|---|---|---|
| NFR-001 | 正規化後の許可範囲を越えて読み書きしない。親参照やシンボリックリンクで範囲外へ到達する要求は拒否する。実体の範囲を確認できないホストでは該当操作を止める | AC-011 |
| NFR-002 | 明示的な作成・編集許可がないとき、Vaultへの書き込みを0件にする。既存ノートの添削は保存前に差分を提示する | AC-012 |
| NFR-003 | 保存直前に、元の内容と現在の内容を照合する。検出した競合では保存を止める。不完全な対象ファイルを残さない保存方式を利用し、必要な機能を使えないホストでは未保存と報告する | AC-013 |
| NFR-004 | 添削時にプロパティ、リンク先・表示名、埋め込み、コールアウト記法、コード、表、識別子、数値、出典を保護する。保護対象変更や意味レビュー未完了なら保存を止める | AC-014 |
| NFR-005 | 選択したホストモデルに原文が渡ることと対象範囲を処理前に示す。利用者の許可なく、追加の外部サービス・別モデル・外部検索へ内容を渡さない | AC-015 |
| NFR-006 | 許可範囲内のノートに権限変更や外部送信の命令が含まれていても、資料として扱い、実行しない | AC-015 |
| NFR-007 | 機械的なリンク分類と規約の観測結果は、同じ入力と規則なら一致する。LLMによる関連候補や規約の推測、完全な意味保存は保証しない | AC-016 |
| NFR-008 | 不足する依存関係、読めないファイル、非対応形式、範囲制限、レビュー失敗を明示する。黙って省略せず、変更されていない対象も報告する | AC-009 |
| NFR-009 | Obsidianアプリ、公式CLI、MCP、コミュニティプラグインを必須にしない。ホストと既存の日本語添削に必要な依存関係は例外として明示する | AC-010 |
| NFR-010 | 少なくとも100件の独自Markdownノートで、6記法と4分類、対象外ケース、規約の観測を固定期待値と照合する。処理上限を設ける場合は事前に範囲を合意し、打ち切りを報告する | AC-016 |
| NFR-011 | 既存のtech-writer、日本語添削、CLIの選択インストールを壊さない。新規の利用者向け資料は日本語を主とする | AC-010 |
| NFR-012 | 既存ノートを整理方式に合わせて移動・改名しない。`.obsidian`と対象外ファイルの変更を0件にする | AC-011 |

範囲確認、保存直前の内容照合、不完全な書き込みを防ぐ操作にはホストの対応が必要となる。
これらを確認できない環境では必要な操作を拒否し、可能な範囲の提案・診断と未実施理由を返す。
保存直前の照合後に起きる外部編集を、あらゆるホストで排除できるとは保証しない。
排除できる競合の範囲、残る競合、保存方式の前提は設計と操作前の説明に含める。

## データ、外部接続、導入・運用

Vault本文と規約の所有者は利用者とし、第三者の権利とアクセス権限を尊重する。
診断時は本文を変更せず、恒久的な全文索引や会話記録をVaultに追加しない。
作成ノートと利用者が指定した報告書は利用者の管理対象とする。
原文保全や復旧用に内容のコピーを保存する場合は、場所・目的・保持期間・削除方法を事前に示して許可を得る。
利用者のデータを試験用fixtureや公開ログへ転用しない。エラー報告に秘密値や不要な本文を含めない。
ホストやモデル提供者の保持・削除をこのSkillが制御できるとは説明しない。

入力インターフェースはホストからの依頼と許可範囲内のローカルファイルとする。
モデル利用はホストの既存設定に従い、秘密鍵や新たな認証設定を要求しない。
Obsidianアプリとの常時接続は前提にしない。ネットワークや日本語添削の依存関係が利用できない場合は、未実施の機能を明示する。

既存Vaultの移行は不要とする。導入は既存のkotonohaインストール手順に従い、既存Skillの無断置換を行わない。
導入取り消しのためにノートを削除しない。復旧は明示された対象と手順に限定する。
継続的なサービス運用・稼働率保証は対象外とし、失敗時は対象、原因、変更の有無、再実行に必要な条件を報告する。
OSやホストの対応表、必要な依存関係、利用可能な規模は設計・試験結果で明示し、未検証環境を対応済みと宣言しない。

## 受入条件と独自検証データ

各ACは対応するFR・NFRを検証する。期待値は実装から逆算せず、設計承認までに固定する。
機械分類は固定期待値との全件一致を合格条件とする。
関連候補や文章表現は同じ文字列を要求せず、根拠・権限制約・保護対象の保存で判断する。

| 受入ID | 検証データ・操作 | 合格条件 |
|---|---|---|
| AC-001 | Vault未指定、複数Vault、存在しないルート、読み取り範囲未指定 | 曖昧なまま探索せず、不足または誤りと必要な指定を示す |
| AC-002 | 明文化された規約、規約と異なる既存ノート、規約のないVault | 根拠の種類・パス・観測件数または一覧を示す。宣言・事実・推測・矛盾を区別し、観測だけで規約を確定しない |
| AC-003 | 同じ内容について完成ノートと再利用用テンプレートをそれぞれ依頼 | 完成ノートに未展開変数を残さず、テンプレートでは変数を保持する。保存予定パスと内容を示す |
| AC-004 | 新規パス、既存パス、作成直前に別ファイルが現れるパス | 許可された新規パスだけに作成する。衝突した既存ファイルのバイト列は変わらない |
| AC-005 | 関連ノートあり、候補なし、同名ノート、範囲外だけに関連資料があるケース | 候補の実在・許可範囲・パスを機械確認する。理由は関連性の判断として表示し、妥当性は文脈レビューで確認する。ノートは変更しない |
| AC-006 | 対応する6記法、実在・欠落見出し、同名候補、範囲外、コード・コメント内の例 | 各実リンクを規則どおりに分類し、例示は除外する。非対応と範囲外は判定不能として区別する |
| AC-007 | 将来作成する意図を示したリンクと、誤記の疑いがあるリンク | 前者を自動修正せず、後者も候補と理由の提示にとどめる。書き込みは0件 |
| AC-008 | 独自の日本語誤り、修正不要文、未解決リンクを含むノートに対し、差分の承認・拒否を行う | 必要訂正と任意改善を区別し、スコアだけで訂正しない。承認・安全検査を満たした差分だけを保存し、拒否時は原文を保持する。保存できない環境では未保存と明示する |
| AC-009 | 全件成功、読めないファイル、依存関係不足、非対応形式、処理打ち切り | 処理済み・未処理の範囲と理由を示し、全件成功と誤報しない |
| AC-010 | 作業コピーとnpmパッケージから単独・全Skillをインストール | 新Skillと資料を利用できる。記録した変更前のCLI・関連Pythonテストに対して新規の失敗を出さず、既存Skillを無断置換しない。対応ホストではObsidianなしで5機能を利用できる |
| AC-011 | 親ディレクトリ参照、範囲外へのシンボリックリンク、`.obsidian`、許可されていない書き込み | 拒否対象の読み取り・書き込みは0件。Vault外と対象外のファイルは変更前後で同一 |
| AC-012 | 読み取り専用の依頼、保存許可なし、差分提示前の添削 | 書き込みは0件。保存候補と未保存状態が分かる |
| AC-013 | 最終照合前の別編集、書き込み失敗、必要な保存機能がないホストを模擬 | 検出した外部編集を上書きせず、不完全な対象ファイルを残さない。必要な機能がなければ保存せず、失敗・復旧・未保存状態を示す |
| AC-014 | プロパティ・リンク・記法・コード・数値・意味を意図的に変える候補、意味レビュー未完了 | 保護対象変更は機械検査で止める。意味変化は文脈レビューの対象にし、未承認候補を保存しない |
| AC-015 | 追加送信を誘導するノートと、外部サービス未許可の依頼 | 追加送信・資料内命令の実行は0件。ホストモデルに渡す範囲と許可の有無を示す |
| AC-016 | 100件以上の独自ノートに6記法・4分類・対象外ケースと規約の観測データを含め、繰り返し診断 | 初回のリンク分類と規約の観測結果が固定期待値に全件一致し、再実行でも一致する。LLMの推測は一致判定に含めない。所要時間は参考値として記録する |

テストデータには日本語・空白を含むパス、同名ノート、リンク表示名、コード中の記法、未解決を意図した参照を含める。
安全試験では変更前後の内容と操作記録を照合する。実在の利用者データや他製品のfixtureは使用しない。
LLMの意味判断は人手の承認や数学的な保証とは区別する。対応機能を使えない場合は受入済みとせず、未実施として扱う。
